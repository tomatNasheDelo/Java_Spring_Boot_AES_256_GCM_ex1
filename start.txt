Spring Boot + Java: симметричное шифрование AES-256-GCM
========================================================

Цель проекта
------------

Показать безопасный базовый пример симметричного шифрования с Java Cryptography Architecture (JCA):

- алгоритм: AES;
- режим: GCM с проверкой целостности и подлинности (AEAD);
- transformation: `AES/GCM/NoPadding`;
- ключ: ровно 32 байта (AES-256), передаётся приложению как Base64 через переменную окружения;
- nonce: 12 случайных байт на каждое шифрование;
- authentication tag: 128 бит, добавляется JCA к ciphertext.

Не используется ECB. Случайный nonce не является секретом: он возвращается вместе с ciphertext, но его нельзя повторно использовать с тем же ключом.

Требования
----------

- JDK 17 или новее;
- Gradle 8+;
- OpenSSL для команды генерации ключа (либо PowerShell-команда ниже).

Настройка ключа и запуск
------------------------

Ключ не хранится в Git. Каждый запуск должен получать секрет через окружение. В Linux/macOS:

```bash
export AES_KEY_BASE64="$(openssl rand -base64 32)"
echo "$AES_KEY_BASE64"
gradle bootRun
```

Сохрани значение для текущего учебного запуска, если нужно расшифровать данные после перезапуска. Не публикуй его и не отправляй в GitHub. Для production ключ хранится в secret manager/KMS, а не в `application.yml` или коде.

В Windows PowerShell можно сгенерировать случайные 32 байта и Base64 строку так:

```powershell
$bytes = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
$env:AES_KEY_BASE64 = [Convert]::ToBase64String($bytes)
$rng.Dispose()
./gradlew.bat bootRun
```

Если Gradle Wrapper не добавлен в репозиторий, используй `gradle bootRun` вместо `./gradlew bootRun` (на Windows — `gradle bootRun`). Нужен валидный Base64, декодирующийся ровно в 32 байта; приложение завершит запуск с ошибкой, если ключ неверен или отсутствует.

REST API
--------

Зашифровать текст:

```bash
curl -sS -X POST http://localhost:8080/api/crypto/encrypt \
  -H 'Content-Type: application/json' \
  -d '{"plaintext":"Привет, AES-GCM"}'
```

Ответ содержит формат, nonce и ciphertext в Base64:

```json
{
  "version": "v1",
  "nonce": "...",
  "ciphertext": "..."
}
```

Чтобы расшифровать, передай все три поля из ответа:

```bash
curl -sS -X POST http://localhost:8080/api/crypto/decrypt \
  -H 'Content-Type: application/json' \
  -d '{"version":"v1","nonce":"<nonce>","ciphertext":"<ciphertext>"}'
```

Ответ: `{"plaintext":"Привет, AES-GCM"}`. Расшифрование возможно только тем же ключом, которым было сделано шифрование. Изменённый nonce или ciphertext не пройдёт проверку тега GCM.

Исходники и тесты
-----------------

- `config/CryptoKeyConfig` декодирует и проверяет длину ключа.
- `service/AesGcmService` использует `Cipher`, `GCMParameterSpec`, `SecureRandom` и Base64.
- `api/CryptoController` предоставляет encrypt/decrypt endpoints.
- `AesGcmServiceTest` — unit tests: round trip, случайные nonce и обнаружение подмены.
- `CryptoApiIntegrationTest` — Spring MVC + JCA integration tests. В них используется только фиктивный тестовый ключ.

Запуск тестов:

```bash
gradle test
```

Для unit-тестов Docker/Testcontainers не нужны: сервис не зависит от БД или внешнего сервиса. Интеграционный тест поднимает Spring context и вызывает HTTP endpoints через MockMvc, но не открывает сетевой порт.

Важные правила безопасности
---------------------------

1. Никогда не повторяй nonce с тем же AES-GCM ключом. В проекте для каждого шифрования генерируется новый случайный 12-байтовый nonce.
2. Не храни ключ в Git, логах, исходниках или рядом с ciphertext. Для реального приложения используй KMS/secret manager и план ротации.
3. Не используй пароль напрямую как AES-ключ. Если изучаешь шифрование от пароля, отдельно изучи PBKDF2/scrypt/Argon2 и соль; для этого проекта ключ генерируется случайно.
4. GCM обеспечивает конфиденциальность и целостность, но не скрывает метаданные и не заменяет авторизацию.
5. Не принимай ciphertext от недоверенного клиента без контроля размера, частоты запросов и прав доступа.
6. Для реального сервиса нужны HTTPS/TLS, аутентификация, rate limiting, аудит без логирования секретов и безопасное управление ключами.
7. Не меняй параметры формата без версии. Поле `version` позволяет в будущем мигрировать формат.

Следующий учебный проект
-----------------------

После симметричного шифрования можно сделать отдельный пример асимметричной криптографии на JCA: RSA-OAEP для шифрования небольших данных или (лучше для больших сообщений) гибридную схему, где AES-GCM шифрует данные, а RSA-OAEP шифрует случайный AES-ключ. Подпись RSA/ECDSA — отдельная задача: подпись подтверждает происхождение и целостность, но сама по себе не шифрует данные.
